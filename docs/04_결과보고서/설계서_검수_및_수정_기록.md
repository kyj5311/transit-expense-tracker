결과보고서 작성용 기초 자료. 구현을 마친 뒤 설계서 v1.6과 실제 코드를 대조해 검수하고,
발견한 문제를 수정한 과정을 정리한다.

|---|---|

### 1.3 우선순위 결정 근거

작업 순서는 "설계서 10장 테스트에서 바로 실패하는가 / 데이터가 사라질 수 있는가 → 설계서에 명시된 기능 누락 → 비기능·문서 정합성" 기준으로 정했다.

| 우선순위 | 항목 | 이유 |
|---|---|---|
| P1 | 1, 2, 3 | 10장 "저장 중 강제 오류 주입 테스트"·"임의 입력 테스트"에서 즉시 실패, 데이터 손실 가능 |
| P2 | 4, 5, 6 | 설계서·제안서에 명시된 기능 누락 |
| P3 | 7, 8 | 비기능 요구사항(유지보수성·안정성) |

6번은 설계서 내부에서 서술이 엇갈렸다(4.1·4.2·5.2에는 직접 입력이 있으나 3.3 흐름·7.1 화면 목록·그림 7 목업에는 없음). 범위를 줄이는 안과 구현하는 안을 비교한 뒤, 제안서 FR-03에 명시된 요구사항이라는 점을 근거로 구현하기로 결정했다.

### 1.4 발주자 검수 결함 조치

발주자(정유운)의 소프트웨어 검수 보고서 v1.0(검수일 2026-09-28, 종합 판정 **부적합**)과 시험 보고서 v1.0에서

**설계 결정 (영향 분석 후 작성자 결정)**

- 전체 초기화 대신 **깨진 항목만 제외**: 한 건이 깨졌다고 정상 템플릿·내역까지 지우지 않기 위함
- 형태 검사는 **앱이 멈추지 않는 데 필요한 필드만** 확인: 교통수단·지역·요금등급까지 검사하면, `findFare()`가 이미 0원으로 안전하게 처리하는 예전 데이터까지 지워지기 때문
- 요금 데이터는 기본값과 "같은지"가 아니라 **형태만** 검사: '구미'가 없는 예전 요금 데이터도 기존처럼 유지
- 검사는 `StorageModule.load()`가 아니라 각 모듈의 init 함수에 둠: 올바른 형태는 데이터마다 다르므로 데이터를 소유한 모듈이 판단(4.1 모듈 책임). `save`/`load` 시그니처(6.2)는 변경 없음
- 템플릿·내역은 로드 시 저장소를 바로 덮어쓰지 않음 (기존 JSON 파싱 실패 처리와 동일한 방침). 다음 등록·수정·삭제 때 정상 목록으로 저장됨

**조건부 적합 항목에 대한 의견**

- FR-06: 시험 보고서의 근거("템플릿 수정 불가")는 템플릿 수정 기능(`92c13d9`, 9/29) 반영 이전 버전 기준. 최신 버전으로 재검수 요청 예정
- EH-01: 결합 문자(zalgo)가 든 이름이 표 레이아웃을 깨뜨림. 데이터·기능 영향은 없음. 입력 길이 제한·셀 넘침 처리로 보완 예정

## 4. 남은 제한사항

설계 범위상 구현하지 않았거나 알려진 제약.

- 백업/내보내기 기능 없음: 브라우저 데이터를 지우면 복구 불가 (설계서 5.3·9.2에서 범위 제외로 명시)
- 새 지역을 코드에 추가해도, 이미 요금 데이터가 저장된 브라우저에는 자동 반영되지 않음 (초기화 필요). 이때 해당 지역 내역은 0원·"요금 정보 없음"으로 표시됨
- 사용 내역 수정은 노선명·구분·환승만 가능 (지역·요금등급은 수정 불가)
- 직접 등록의 등록 시각은 버튼을 누른 시각으로 고정 (지난 이동을 과거 시각으로 기록하는 기능 없음)
- 저장 실패 시 별도 팝업 없이 화면 안내 문구·콘솔 로그로만 알림 (설계서 9.2 방침)
- 저장된 데이터가 손상되어 로드에 실패하면 앱은 빈 목록으로 시작한다. 손상된 원본은 그대로 남지만,
  그 상태에서 새 내역을 등록하면 새 목록으로 덮어써진다 (손상된 데이터는 어차피 읽을 수 없으므로
  복구 기능은 백업/내보내기와 함께 향후 개선 사항으로 둔다. 2.1 EH-02 로드 오류 테스트에서 확인)
- 파싱은 되지만 형태가 틀린 데이터(ERROR-01)도 같은 방침: 요금 데이터는 기본값으로 초기화, 템플릿·내역은
  깨진 항목만 제외하고 시작하며 제외 사실은 콘솔 경고로만 알린다 (1.4)
